AWS Cloud Kya Hai? Services, Pricing aur Shuruaat ki Guide

AWS आज दुनिया का सबसे बड़ा cloud platform है, और भारत में भी छोटी startups से लेकर बड़े enterprises तक इसका इस्तेमाल होता है। पर पहली बार अंदर जाने पर सबसे बड़ी दिक्कत सेवाओं की संख्या नहीं, यह समझना होता है कि कौन सी सेवा किस काम के लिए है और बिल आखिर इतना बड़ा कैसे बन जाता है।

इस आर्टिकल में मैं बताऊँगा कि AWS cloud क्या है, region और availability zone का मतलब, वे छह सेवाएँ जो शुरुआत में 90 प्रतिशत काम के लिए काफी हैं, pricing का असली गणित, पहला setup किन छह कदमों में करें, खर्च कम करने के आठ व्यावहारिक तरीके, कब AWS ज़रूरत से ज़्यादा हो जाता है, और वे पाँच गलतियाँ जो नए लोग सबसे ज़्यादा करते हैं।

छोटा जवाब: AWS एक cloud platform है जहाँ आप servers, storage, database और कई सेवाएँ किराए पर लेते हैं और उपयोग के हिसाब से भुगतान करते हैं। शुरुआत के लिए EC2 (server), S3 (storage), RDS (database), IAM (access) और VPC (network) समझ लेना काफी है। सबसे ज़रूरी कदम है — पहले दिन से billing alarm लगाना।

AWS cloud kya hai

AWS का मतलब Amazon Web Services है। इसमें सैकड़ों सेवाएँ हैं, पर उनका ढाँचा एक ही है — आप एक account बनाते हैं, एक region चुनते हैं, और जो चीज़ चाहिए उसे चालू करते हैं। उपयोग के हिसाब से बिल बनता है।

पारंपरिक hosting में आप महीने के हिसाब से एक server लेते थे, चाहे उस पर काम हो या न हो। यहाँ आप घंटे या सेकंड के हिसाब से देते हैं, और जब ज़रूरत न हो तो बंद कर सकते हैं। यही लचीलापन AWS का सबसे बड़ा फायदा है — और सबसे बड़ा जोखिम भी, क्योंकि भूली हुई चीज़ें चुपचाप बिल बढ़ाती रहती हैं।

Region aur availability zone

Region एक भौगोलिक क्षेत्र है, जैसे मुंबई। हर region के अंदर कई availability zones होते हैं — अलग data centres जो बिजली और network में एक-दूसरे से स्वतंत्र होते हैं।

यह बँटवारा इसलिए है कि अगर एक data centre में दिक्कत आए, तो सेवा न रुके। इसलिए production में कम से कम दो availability zones में चीज़ें रखने की सलाह दी जाती है। साथ ही region का चुनाव data के कानूनी पक्ष और latency, दोनों से जुड़ा होता है।

Console, CLI aur API

एक ही काम तीन तरह से हो सकता है — browser में console से, command line से, या code में API के ज़रिए। शुरुआत में console सीखना आसान है, पर असली काम CLI और code से होता है, क्योंकि वही दोहराया जा सकता है और version control में रखा जा सकता है।

यह आदत शुरू से बनाएँ — जो चीज़ console से बनाई है, उसे बाद में code या template में लिखें। वरना कुछ महीनों बाद आपको याद नहीं रहेगा कि कौन सी setting कहाँ बदली थी।

Chhe services jo shuruaat me kaafi hain

सेवाकामआम गलती
EC2Virtual serverबंद न करना, बड़ा size चुनना
S3File storagePublic bucket बना देना
RDSManaged databaseBackup और retention न देखना
Lambdaबिना server code चलानाहर काम के लिए इसे चुनना
IAMAccess और permissionsसबको admin देना
VPCNetwork का ढाँचाDefault VPC को production मान लेना

EC2 वह virtual machine है जिस पर आप कुछ भी चला सकते हैं। इसे उसी तरह संभालें जैसे अपने server को — updates, firewall, backup।

S3 files रखने की जगह है — images, backups, documents। यह बहुत सस्ता और टिकाऊ है, पर इसकी permissions गलत सेट हों तो data सार्वजनिक हो सकता है।

RDS database को manage करता है — backup, patching और replication provider संभालता है। इससे समय बचता है, पर इसकी कीमत और सीमाएँ समझ लेनी चाहिए।

Lambda तब अच्छा है जब काम कभी-कभी आता हो और लंबा चलने वाला server बनाना बेकार हो। हर request पर बिल बनता है, इसलिए लगातार भारी काम के लिए यह महंगा पड़ सकता है।

IAM तय करता है कि कौन क्या कर सकता है। इसे शुरुआत में ही ठीक करें — एक admin account, बाकी काम के लिए सीमित अनुमतियाँ, और root account पर MFA।

VPC आपका निजी network है। इसमें subnets, route tables और security groups आते हैं। शुरुआत में default VPC से काम चल जाता है, पर production में अपना ढाँचा बनाना बेहतर रहता है।

Pricing kaise kaam karti hai

AWS का बिल चार चीज़ों से बनता है — compute (server का समय), storage (जगह), network (data transfer) और अतिरिक्त services (database, queue, monitoring)। सबसे ज़्यादा चौंकाने वाला हिस्सा अक्सर network होता है, क्योंकि data transfer का हिसाब लोग भूल जाते हैं।

Compute ke chaar tarike

  • On-demand — जितना चलाएँ, उतना दें। लचीला, पर सबसे महंगा।
  • Savings plan / reserved — एक या तीन साल की प्रतिबद्धता पर कम दाम।
  • Spot — खाली क्षमता सस्ते में, पर कभी भी बंद हो सकती है।
  • Serverless — request के हिसाब से, बिना server सोचे।

शुरुआत में on-demand ठीक है, क्योंकि आपको अपना उपयोग पता ही नहीं होता। दो-तीन महीने के आंकड़े आने के बाद देखें कि कौन सी चीज़ लगातार चल रही है — उसी पर savings plan लें।

Free tier की सच्चाई

AWS का free tier कुछ सेवाओं को सीमित समय या सीमित मात्रा में मुफ्त देता है। यह सीखने के लिए अच्छा है, पर दो बातें याद रखें — पहली, हर सेवा मुफ्त नहीं है; दूसरी, सीमा पार होते ही सामान्य दाम शुरू हो जाते हैं।

कई लोगों का पहला बिल इसी वजह से बड़ा आता है कि उन्होंने एक बड़ा server चालू छोड़ दिया या NAT gateway जैसी चीज़ बनाकर भूल गए। free tier का मतलब "सब मुफ्त" कभी न समझें।

Pehla setup: chhe kadam

कदम 1 — account और root सुरक्षा। Account बनाएँ, root पर मजबूत password और MFA लगाएँ, और रोज़ के काम के लिए root का इस्तेमाल कभी न करें।

कदम 2 — billing alarm। महीने का एक छोटा बजट तय करें, जैसे 500 रुपये, और उसके 50 प्रतिशत पर alert लगाएँ। यह पाँच मिनट का काम है और हज़ारों का बचाव कर सकता है।

कदम 3 — IAM user। अपने लिए एक अलग user बनाएँ, जिसे सिर्फ ज़रूरी अनुमतियाँ हों। बाद में जब टीम बढ़े, तो हर व्यक्ति के लिए अलग पहचान रखें।

कदम 4 — region तय करें। भारत के उपयोगकर्ताओं के लिए मुंबई region आम चुनाव है। ध्यान रखें कि region बदलने पर कीमतें और सेवाएँ दोनों बदल सकती हैं।

कदम 5 — एक छोटा server। सबसे छोटे size से शुरू करें, security group में सिर्फ ज़रूरी ports खोलें, और काम खत्म होने पर बंद करें।

कदम 6 — storage और backup। एक S3 bucket बनाएँ, public access बंद रखें, और versioning चालू करें। पहले ही दिन से backup की आदत बनाएँ।

Kharcha kam karne ke 8 tarike

  1. जो server चल नहीं रहा, उसे बंद करें — बिल घंटे के हिसाब से बनता है।
  2. सही size चुनें; बड़ा server हमेशा ज़रूरी नहीं होता।
  3. Storage को सही class में रखें — पुराने backup सस्ते tier में जा सकते हैं।
  4. Data transfer की दिशा देखें; एक ही region में रखने से कई बार बचत होती है।
  5. Snapshot और पुराने images साफ करें, वरना वे सालों तक बिल बढ़ाते रहेंगे।
  6. Budget और alarm हर अलग environment पर लगाएँ।
  7. महीने में एक बार बिल का breakdown पढ़ें, सिर्फ कुल रकम नहीं।
  8. जो चीज़ लगातार चल रही है, उसके लिए savings plan लें।

इनमें पहला और पाँचवाँ सबसे ज़्यादा बचत देते हैं। पर उनका फायदा तभी है जब आप महीने में एक बार बिल खोलकर देखें — वरना पता ही नहीं चलेगा कि कहाँ से पैसा जा रहा है।

AWS kab zaroorat se zyada hai

अगर आपकी वेबसाइट पर महीने में कुछ हज़ार लोग आते हैं, एक छोटा database है और कोई जटिल infrastructure नहीं, तो एक साधारण VPS या managed hosting सस्ता और आसान रहेगा। AWS की ताकत बड़े पैमाने, अलग-अलग सेवाओं और लचीलेपन में है — जहाँ उनकी ज़रूरत नहीं, वहाँ जटिलता ही मिलती है।

यह भी देखें कि क्या आपके पास इसे संभालने वाला कोई है। Cloud का बिल और security दोनों ध्यान माँगते हैं। बिना मालिक वाला cloud account धीरे-धीरे अनियंत्रित हो जाता है।

Monitoring aur support

Cloud में सबसे खतरनाक स्थिति वह है जब कुछ टूटा हो और किसी को पता न हो। इसलिए शुरुआत में तीन चीज़ें लगाएँ — CloudWatch जैसे metrics, एक alert जो email या phone पर जाए, और एक साधारण dashboard जो रोज़ देखा जाए।

Alert कम रखें, पर सही रखें। चार चीज़ों पर नज़र रखें — server का CPU और memory, disk की जगह, error rate और billing। इनमें से कोई भी तय सीमा पार करे, तो सूचना मिले।

Support plan का चुनाव भी सोच-समझकर करें। बुनियादी plan में जवाब देर से आता है, जो सीखने के लिए ठीक है पर production के लिए नहीं। अगर आपका काम ग्राहक पर निर्भर है, तो भुगतान वाला plan उस एक रात के इंतज़ार से सस्ता पड़ सकता है।

Domain, certificate aur backup

कई लोग server बना लेते हैं पर domain और HTTPS भूल जाते हैं। Route 53 जैसी सेवा से domain जोड़ें, और certificate manager से free certificate लगाएँ। इसके बाद ही site भरोसेमंद दिखती है और browser चेतावनी नहीं देता।

Backup को अलग रखें — अलग region या अलग account में। जो backup उसी account में है जहाँ गलती हुई, वह अक्सर उसी गलती में चला जाता है। महीने में एक बार restore करके देखें, वरना backup होने का भरोसा सिर्फ कागज़ी रहेगा।

5 galtiyan jo sabse aam hain

पहली — root account से रोज़ का काम करना। दूसरी — billing alarm न लगाना। तीसरी — S3 bucket को public कर देना। चौथी — security group में सब ports खोल देना। पाँचवीं — console में बदलाव करके उसे कहीं दर्ज न करना।

तीसरी गलती सबसे खतरनाक है, क्योंकि उसका पता कभी-कभी महीनों बाद चलता है। S3 में public access block चालू रखें और bucket policy समय-समय पर जाँचें।

मैंने इससे क्या सीखा

सबसे बड़ी सीख यह रही कि cloud में खर्च अनुशासन से काबू में रहता है, तकनीक से नहीं। जिन accounts में हमने पहले दिन से budget, tags और monthly review रखा, उनका बिल कभी चौंकाने वाला नहीं आया। जहाँ सिर्फ "बाद में देखेंगे" चला, वहाँ कुछ महीनों में ऐसी सेवाएँ चालू मिलीं जिनकी ज़रूरत ही नहीं थी।

दूसरी सीख — छोटी शुरुआत हमेशा बेहतर है। सबसे छोटे server और सबसे साधारण setup से शुरू करें, फिर ज़रूरत दिखने पर बढ़ाएँ। बड़े setup से शुरू करने पर न सिर्फ बिल बढ़ता है, बल्कि यह समझना भी मुश्किल हो जाता है कि कौन सा हिस्सा ज़रूरी है।

तीसरी सीख — AWS सीखना एक हफ्ते का काम नहीं, पर शुरुआत के लिए पाँच सेवाएँ काफी हैं। जो लोग पहले दिन से हर सेवा समझने की कोशिश करते हैं, वे अक्सर कुछ भी पूरा नहीं कर पाते।

अक्सर पूछे जाने वाले सवाल

क्या AWS सीखने के लिए पैसे लगते हैं?

कुछ सेवाएँ free tier में आती हैं, पर पूरी तरह मुफ्त नहीं। छोटे server और थोड़े storage पर महीने का खर्च कम रखा जा सकता है, बशर्ते आप चीज़ें बंद करना न भूलें।

क्या AWS छोटी website के लिए ठीक है?

तकनीकी रूप से हाँ, पर ज़रूरी नहीं। छोटी site के लिए सस्ता VPS या managed hosting अक्सर आसान और सस्ता रहता है।

सबसे पहले कौन सी सेवा सीखें?

EC2 और S3 से शुरुआत करें, साथ में IAM की बुनियादी समझ लें। इसके बाद RDS और VPC पर आएँ।

बिल अचानक बढ़ जाए तो क्या करें?

Cost explorer में सेवा के हिसाब से breakdown देखें, बिना इस्तेमाल हो रहे resources बंद करें, और snapshot तथा पुराने storage साफ करें।

क्या AWS में data भारत में रहेगा?

अगर आप मुंबई region चुनते हैं और backup भी उसी region में रखते हैं, तो data भारत में रहता है। इसे contract और settings, दोनों में जाँचें।

Infrastructure की बुनियादी समझ के लिए server cluster की गाइड पढ़ें, containers के साथ आगे बढ़ने के लिए orchestration वाला आर्टिकल देखें, और data कहाँ रहेगा यह तय करने के लिए sovereign cloud की गाइड पढ़ें।

आगे पढ़ें: सेवाओं की आधिकारिक जानकारी AWS documentation पर और कीमतों का ताज़ा हिसाब AWS pricing पेज पर देखें। कीमतें और free tier की शर्तें बदलती रहती हैं।
