System design वह काम है जिसमें तय होता है कि आपकी app एक हज़ार users पर भी चले और एक लाख पर भी — बिना हर हफ़्ते server बदलने के। यह कोई एक tool या framework नहीं है; यह सवाल पूछने का तरीका है: कितने users, कितनी request, कितना data, कितनी देरी चलेगी, और क्या चीज़ खराब हो सकती है।

इस guide में मैं वही बुनियादी चीज़ें खोलूँगा जो हर interview और हर असली project में काम आती हैं — चार शुरुआती सवाल, vertical और horizontal scaling, load balancer, cache, database के बुनियादी फैसले, और एक छोटा photo-sharing app का design step-by-step. अंत में वे पाँच गलतियाँ हैं जो शुरुआती engineers सबसे ज़्यादा करते हैं।

छोटा जवाब: System design में पहले numbers निकालें — कितनी request प्रति सेकंड, कितना data, कितना read और कितना write. फिर उसी हिसाब से सबसे सादा setup चुनें: एक server, एक database, ऊपर एक cache. जब वह हद पर पहुँचे, तब load balancer और दूसरा server जोड़ें। जो design बिना ज़रूरत के जटिल है, वह बड़ी system नहीं, बड़ी मुसीबत है।

System design kya hai

एक ही feature को कई तरह से बनाया जा सकता है। "User अपनी profile photo बदल सके" — यह एक line का feature है, पर उसके पीछे तय करना पड़ता है: photo कहाँ रखेंगे, कितने size में, कौन देख सकता है, पुरानी photo कब तक रखेंगे, और अगर storage भर जाए तो क्या होगा। System design इन्हीं फैसलों का नाम है।

अच्छा design तीन चीज़ें करता है। पहला — ज़रूरत से ज़्यादा नहीं करता; जिस चीज़ की ज़रूरत नहीं, उसे नहीं जोड़ता। दूसरा — बढ़ने की जगह छोड़ता है, यानी आज एक server से चल सके और कल तीन जोड़ सकें बिना code फिर से लिखे। तीसरा — खराबी मानकर चलता है; मान लेता है कि कोई server बंद होगा, कोई request fail होगी, और उसके लिए रास्ता रखता है।

चार सवाल जो हर design से पहले पूछें

1. कितने users और कितनी request? "बहुत सारे" एक जवाब नहीं है। 10,000 daily users और 10 लाख daily users के design में ज़मीन-आसमान का फर्क है। शुरुआत में एक rough calculation काफ़ी होती है: daily users × प्रति user request ÷ 86,400 = average request per second. Peak आमतौर पर average का 3–5 गुना होता है, त्योहार या sale के दिन और ज़्यादा।

2. Read ज़्यादा है या write? Blog, catalogue और profile pages में read 90% से ज़्यादा होते हैं — वहाँ cache सबसे बड़ा हथियार है। Payment, chat और logging में write ज़्यादा होते हैं — वहाँ queue और database की लिखने की क्षमता मायने रखती है।

3. कितना data और कितने साल? एक user का record 2 KB है या 2 MB, यह तय करता है कि सब एक database में रहेगा या बाँटना पड़ेगा। साथ में यह भी सोचें कि data कब तक रखना है — हर चीज़ हमेशा के लिए रखना सबसे महंगा फैसला है।

4. कितनी देरी और कितनी downtime चलेगी? एक dashboard के लिए 2 सेकंड ठीक है; payment page के लिए 200 मिलीसेकंड चाहिए। और "साल में 1 घंटा बंद" बनाम "कभी बंद नहीं" — दूसरे के लिए आपको दुगुना खर्च और दुगुनी जटिलता चुकानी पड़ेगी।

Scaling: बड़ा server या ज़्यादा server

Vertical scaling का मतलब है एक ही server में CPU, RAM या disk बढ़ाना। यह सबसे आसान है — code में कुछ नहीं बदलता, बस plan बदलती है। पर हर machine की एक हद होती है, और बड़ी machine का खर्च तेज़ी से बढ़ता है। छोटी team के लिए शुरुआत यहीं से सही है।

Horizontal scaling का मतलब है server की गिनती बढ़ाना और आगे load balancer लगाना। इसकी असली शर्त यह है कि आपकी app "stateless" हो — यानी किसी भी server पर request जाए, जवाब वही मिले। अगर session या uploaded file सिर्फ़ एक server की disk पर है, तो दूसरा server उसे नहीं जानता। इसीलिए session को Redis जैसी जगह और files को object storage में रखा जाता है।

मेरी सलाह: शुरुआत vertical से करें, पर code ऐसा लिखें कि horizontal कल मुमकिन हो — session बाहर रखें, local file पर भरोसा न करें, और हर server को एक जैसा बनाएँ। यह आदत बाद में महीनों का काम बचा देती है।

Load balancer क्या करता है

Load balancer आने वाली requests को कई servers में बाँटता है। साथ में वह तीन काम और करता है: health check (कौन सा server ज़िंदा है), SSL termination (HTTPS वहीं खत्म हो जाए), और कभी-कभी rate limiting.

बाँटने के कुछ आम तरीके हैं। Round robin बारी-बारी से हर server को request देता है — सबसे सादा। Least connections उस server को भेजता है जिस पर सबसे कम काम चल रहा है — तब अच्छा जब requests का वज़न अलग-अलग हो। IP hash एक ही user को हमेशा एक ही server पर भेजता है — तब काम आता है जब session कहीं local है, पर यह horizontal scaling की भावना के खिलाफ़ है।

एक बात जो अक्सर छूट जाती है: load balancer खुद भी एक हिस्सा है जो fail हो सकता है। Production में इसे दो में रखा जाता है, या managed service इस्तेमाल की जाती है। इस विषय को मैंने server cluster और failover वाली guide में विस्तार से लिखा है।

Cache: सबसे सस्ता जवाब वह है जो काम ही न करे

Cache किसी नतीजे को सस्ती जगह पर रख देता है, ताकि अगली बार वही सवाल महंगी जगह तक न पहुँचे। चार परतें आम हैं। Browser cache — images, CSS और JS user के फोन में ही रहते हैं। CDN — static files दुनिया के किनारों से आते हैं, आपके server तक नहीं आते। App cache (Redis जैसा) — database के नतीजे milliseconds में लौटाता है। Database cache — database अपने अंदर ही कुछ चीज़ें याद रखता है।

Cache का सबसे बड़ा सवाल "कब हटाना है" होता है। तीन आम तरीके हैं: TTL (कुछ मिनट बाद अपने आप हट जाए), write-through (जब data बदले तो cache भी बदले), और cache-aside (पहले cache देखो, न मिले तो database से लाओ और cache में डाल दो)। सबसे आम cache-aside है, क्योंकि इसमें cache बंद भी हो जाए तो app चलती रहती है।

एक चेतावनी: cache में वह data मत रखें जिसे हर बार ताज़ा चाहिए — जैसे bank balance या stock count. और cache को "source of truth" मत बनाएँ; असली data database में रहे, cache सिर्फ़ तेज़ रास्ता हो।

Database: तीन फैसले

SQL या NoSQL? अगर data में रिश्ते हैं, पैसा और transaction हैं, और आपको "हर order के साथ उसका customer" जैसी query चाहिए, तो relational database (PostgreSQL, MySQL) सही है। अगर data बहुत बड़ा, shape बदलता हुआ या document जैसा है, तो document store ठीक रहता है। ज़्यादातर apps के लिए PostgreSQL से शुरुआत करना आज भी सबसे समझदारी है।

Replication: एक primary database जो लिखता है, और एक-दो replica जो पढ़ते हैं। इससे read का load बँटता है और primary बंद होने पर replica आगे आ सकता है। नुकसान यह है कि replica थोड़ा पीछे रह सकता है — यानी आपने अभी जो लिखा, वह पढ़ने में न मिले। इसे replication lag कहते हैं और UI में इसका ध्यान रखना पड़ता है।

Sharding: जब एक database की हद आ जाए, तो data को कई databases में बाँटा जाता है — जैसे user_id के हिसाब से। यह सबसे मुश्किल कदम है, क्योंकि cross-shard query, rebalancing और transactions सब उलझ जाते हैं। इसे तभी करें जब replication और indexing से काम न बने।

एक छोटा design walkthrough

मान लीजिए हमें एक photo-sharing app बनाना है जहाँ लोग photo upload करें और दूसरे देखें। चलिए numbers से शुरू करें।

मानहिसाब
Daily active users2 लाख
प्रति user 10 photo देखना, 0.2 upload20 लाख reads, 40 हज़ार writes प्रति दिन
Average per second~23 reads/s, ~0.5 writes/s
Peak (4x)~90 reads/s, ~2 writes/s
Photo का average size1.5 MB × 40 हज़ार = ~60 GB प्रति दिन

पहला नतीजा: reads writes से 50 गुना ज़्यादा हैं, इसलिए cache और CDN सबसे ज़्यादा फायदा देंगे। दूसरा नतीजा: 60 GB प्रति दिन का मतलब है कि photos database में नहीं, object storage में जाएँगी — database में सिर्फ़ उनका record और link रहेगा।

  1. Upload: app एक pre-signed URL माँगती है, photo सीधे object storage में जाती है, और database में एक row बनती है — user, size, timestamp, visibility.
  2. Thumbnail: upload होने पर एक event निकलता है, एक worker तीन sizes बनाता है। यह काम request के बीच में नहीं, पीछे होता है।
  3. Feed: user के follow किए लोगों की latest photos के IDs cache में रहते हैं। पहली बार database से, उसके बाद cache से।
  4. Serve: photos CDN से जाती हैं, इसलिए app server पर image का load नहीं आता।
  5. Failure: अगर thumbnail worker रुक जाए, तो upload फिर भी सफल रहे — बस thumbnail थोड़ी देर से दिखे। यही "graceful degradation" है।

ध्यान दें कि इस design में अभी एक भी load balancer नहीं है — 90 reads/s एक ठीक server और cache से चल जाते हैं। Load balancer तब जोड़ें जब एक server की हद आए, न कि शुरुआत में ही।

पाँच गलतियाँ जो शुरुआत में होती हैं

1. Microservices से शुरुआत। छह services, छह deployments और आपस में बात करने का ढाँचा — यह सब एक छोटी team को धीमा कर देता है। पहले एक app, अंदर साफ़ modules. जब कोई module अलग करने की असली वजह आए, तब अलग करें।

2. Numbers न निकालना। "Scale के लिए" बहुत सारी चीज़ें जोड़ देना, जबकि असली load 20 requests/s है। पहले नापें, फिर बनाएँ।

3. Cache को सच मान लेना। Cache भर जाए, बंद हो जाए या पुराना हो जाए — app को फिर भी चलना चाहिए। अगर cache हटाते ही app टूटे, तो design में कुछ गलत है।

4. Logs और metrics बाद में। जब तक समस्या आएगी, तब तक data नहीं होगा। शुरुआत से request time, error rate और queue length नापें।

5. Backup को अनदेखा करना। Replication backup नहीं है। गलती से delete हुई row replica में भी delete हो जाएगी। अलग backup और restore की कोशिश — दोनों ज़रूरी हैं।

Mera anubhav

मैंने एक बार एक internal dashboard पर दो हफ़्ते cache और queue जोड़ने में लगाए, क्योंकि मुझे लगा load बहुत है। बाद में metrics देखे तो पता चला कि सबसे धीमी चीज़ एक query थी जो बिना index के चल रही थी, और उसे ठीक करने में एक घंटा लगा। उस दिन के बाद मैंने एक नियम बनाया: किसी भी नई परत से पहले सबसे धीमी जगह नापो।

दूसरी बात जो मैंने सीखी: design का सबसे कीमती हिस्सा diagram नहीं, वह सूची है जिसमें लिखा हो कि क्या चीज़ fail हो सकती है और तब क्या होगा। जब मैं यह सूची बनाता हूँ, तो आधे "ज़रूरी" features अपने आप गिर जाते हैं और डिज़ाइन सादा हो जाता है।

तीसरी बात: cloud का पूरा फायदा तब मिलता है जब आप managed services का इस्तेमाल समझदारी से करें — database, queue, cache और storage पहले managed लें, और अपनी team का समय सिर्फ़ उस business logic पर लगाएँ जो सच में अलग है। AWS Cloud वाली guide में इसका खर्च और शुरुआत दोनों समझाए गए हैं।

नतीजा

System design की शुरुआत tools से नहीं, numbers से होती है। चार सवाल पूछें — कितने users, read या write, कितना data, कितनी देरी — और जो सबसे सादा setup उन numbers को पूरा करे, वही चुनें। Scaling में पहले vertical, फिर horizontal. Cache को तेज़ रास्ता मानें, सच नहीं। Database में पहले replication, बाद में sharding. और हर design के साथ यह लिखें कि क्या टूट सकता है और तब user को क्या दिखेगा। बाकी सब iteration है।

अक्सर पूछे जाने वाले सवाल

क्या system design सीखने के लिए cloud ज़रूरी है?

ज़रूरी नहीं, पर मदद करता है। एक छोटा app deploy करके load balancer, cache और database को असली में चलाकर देखना सबसे तेज़ सीखने का तरीका है।

कितने users पर load balancer चाहिए?

कोई जादुई number नहीं। जब एक server का CPU या response time लगातार बढ़ने लगे, तब जोड़ें। छोटे app के लिए एक अच्छा server महीनों चल जाता है।

Redis cache कब न लें?

जब आपका data बहुत कम हो और query पहले से तेज़ हो। बिना ज़रूरत के cache जोड़ने से सिर्फ़ एक और चीज़ fail होने की जगह बनती है।

SQL बड़े scale पर चलता है?

हाँ। दुनिया की कई बड़ी companies relational database पर चलती हैं, replication और अच्छे index के साथ। NoSQL तब चुनें जब data का shape या size सच में उसकी माँग करे।

Interview में पहले क्या बताएँ?

Requirements और numbers. Interviewer को यही देखना होता है कि आप tools से पहले सवाल पूछते हैं।
