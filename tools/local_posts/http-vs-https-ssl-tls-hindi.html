आपने कभी सोचा है कि browser में वह छोटा ताला क्या बताता है? ज़्यादातर लोग समझते हैं कि "site सुरक्षित है" — पर ताला यह नहीं कहता कि site ईमानदार है, यह सिर्फ़ इतना कहता है कि आपके और server के बीच की बातचीत encrypted है और server ने अपनी पहचान साबित की है। यह फर्क समझना ज़रूरी है, क्योंकि phishing sites भी HTTPS इस्तेमाल करती हैं।

इस guide में मैं HTTP से HTTPS तक का पूरा सफ़र खोलूँगा — encryption में symmetric और asymmetric keys का काम, TLS handshake के steps, certificate कौन बनाता है और browser उसे कैसे जाँचता है, ताला क्या नहीं बताता, और अपनी site पर HTTPS लगाने के practical steps. अंत में वे गलतियाँ भी, जिनकी वजह से ताला आ जाने के बाद भी browser warning देता है।

छोटा जवाब: HTTP data को plain text में भेजता है, इसलिए बीच में कोई पढ़ सकता है। HTTPS वही HTTP है, पर TLS layer के ऊपर — data encrypt होकर जाता है और server अपना certificate दिखाकर साबित करता है कि वह वही है जो होने का दावा कर रहा है। आज हर site पर HTTPS ज़रूरी है, और Let's Encrypt जैसे tools इसे मुफ़्त कर देते हैं।

HTTP aur HTTPS me asli farq

दोनों में request और response का ढाँचा एक जैसा है — method, headers, status codes सब वही। फर्क सिर्फ़ एक layer का है: HTTPS में HTTP की हर बात पहले TLS से गुज़रती है, जो उसे encrypt करके भेजती है। इसीलिए HTTPS को "HTTP over TLS" कहते हैं।

यह छोटा सा फर्क बहुत बड़ा है। सादे HTTP में आपका password, cookie और form data ऐसे ही जाता है — जैसे postcard पर लिखा संदेश, जिसे रास्ते में हर डाकिया पढ़ सकता है। HTTPS उसे sealed envelope बना देता है। और सिर्फ़ पढ़ना ही खतरा नहीं — बीच में बैठा कोई data बदल भी सकता है, जैसे bank के page में अपना account number डाल देना। TLS इसे भी रोकता है।

TLS handshake: das line me poora khel

Connection बनने से पहले browser और server कुछ messages का आदान-प्रदान करते हैं। इसे handshake कहते हैं। इसमें दो चीज़ें तय होती हैं — दोनों एक ही secret key पर सहमत होते हैं, और browser server की पहचान जाँचता है।

  1. Client Hello. Browser कहता है — मैं TLS 1.3 और 1.2 समझता हूँ, ये cipher suites चलते हैं, और यह मेरा random number है।
  2. Server Hello. Server चुनता है कि कौन सा version और cipher चलेगा, अपना random number भेजता है।
  3. Certificate. Server अपना certificate भेजता है, जिसमें public key और domain का नाम होता है।
  4. Verification. Browser जाँचता है कि certificate किसी भरोसेमंद CA ने बनाया है, expire नहीं हुआ, और उसी domain के लिए है।
  5. Key exchange. दोनों मिलकर एक session key बनाते हैं — TLS 1.3 में यह Diffie-Hellman से होता है, और public key से encryption नहीं होती।
  6. Finished. दोनों पुष्टि करते हैं कि handshake बिना बदलाव के पूरा हुआ।
  7. Encrypted data. अब HTTP की हर request और response उसी session key से encrypt होती है।

TLS 1.3 में यह पूरा सफ़र एक round trip में हो जाता है, जबकि TLS 1.2 में दो लगते थे। यही वजह है कि नए servers पर पहला page थोड़ा जल्दी खुलता है। और अगर आपने पहले उसी site से connection बनाया है, तो session ticket की मदद से data पहले message के साथ ही भेजा जा सकता है — इसे 0-RTT कहते हैं।

Symmetric aur asymmetric — dono kyun

यहाँ एक उलझन आती है जो हर किसी को होती है: अगर सब कुछ encrypt करना है, तो key कैसे भेजें? Key को encrypt करने के लिए दूसरी key चाहिए, और उसके लिए तीसरी... यह कभी खत्म नहीं होगा। इसी समस्या का हल है — दो अलग तरह की cryptography एक साथ।

Asymmetric (public key) में दो keys होती हैं: public key जो सबको दी जा सकती है और private key जो सिर्फ़ server के पास रहती है। Public key से encrypt किया हुआ data सिर्फ़ private key से खुलता है। यह धीमा होता है, इसलिए इसे सिर्फ़ शुरुआत में इस्तेमाल करते हैं — या TLS 1.3 में तो सिर्फ़ signature जाँचने के लिए।

Symmetric में एक ही key से encrypt और decrypt होता है। यह बहुत तेज़ है। असली data इसी से encrypt होता है। दिक्कत यह है कि दोनों को वही key चाहिए, और उसे सुरक्षित तरीके से share करना पड़ता है — यही काम Diffie-Hellman जैसे key exchange algorithms करते हैं। वे बिना key भेजे दोनों तरफ़ एक ही secret बना देते हैं।

इसीलिए आधुनिक TLS में public key का काम सिर्फ़ पहचान साबित करना और key exchange में मदद करना है; असली data तेज़ symmetric key से जाता है। इसे hybrid encryption कहते हैं — और यही सब जगह चलता है, बैंक से लेकर WhatsApp तक।

Certificate kaun deta hai

Certificate एक digital document है जिसमें domain का नाम, public key, वैधता की तारीख़ें और जारी करने वाले की जानकारी होती है — और यह सब उस CA (Certificate Authority) के private key से signed होता है। Browser के पास दुनिया के भरोसेमंद CAs की सूची पहले से होती है, इसलिए वह signature जाँच सकता है।

Certificates तीन तरह के होते हैं। Domain Validated (DV) सिर्फ़ यह जाँचता है कि आपका domain पर control है — यह मुफ़्त और सबसे आम है। Organization Validated (OV) में कंपनी के दस्तावेज़ भी जाँचे जाते हैं। Extended Validation (EV) सबसे कड़ी जाँच है, पर आज browsers उसे अलग से नहीं दिखाते — पुराने हरे address bar वाला फर्क अब नहीं रहा।

ज़्यादातर sites के लिए DV पर्याप्त है। ज़रूरी बात यह है कि certificate में लिखा domain आपके URL से मेल खाए। www.example.com और example.com दोनों के लिए एक ही certificate चल सकता है, अगर उसमें दोनों नाम (SAN) हों। वरना browser "certificate name mismatch" देगा — और यह सबसे आम गलती है जो hosting बदलने के बाद होती है।

एक और चीज़ — chain. Server सिर्फ़ अपना certificate नहीं भेजता, बल्कि बीच के certificates भी भेजता है जो उसे root CA तक जोड़ते हैं। अगर बीच का certificate गायब हो, तो कुछ browsers चुपचाप काम कर लेंगे (क्योंकि उनके पास cache है) और कुछ error देंगे। यही वजह है कि "मेरे laptop पर तो ठीक खुलता है" वाली समस्या होती है।

Taala kya batata hai — aur kya nahi

यह हिस्सा सबसे ज़रूरी है, क्योंकि यहीं लोग ठगे जाते हैं।

ताला यह बताता है: आपके और server के बीच की बातचीत encrypted है, data रास्ते में बदला नहीं जा सकता, और server के पास उस domain का valid certificate है। यानी आप जिस address पर गए हैं, वह उसी server पर गया है।

ताला यह नहीं बताता: site अच्छी है, कंपनी असली है, या आपका data ईमानदारी से सँभाला जाएगा। कोई भी व्यक्ति एक domain खरीदकर मुफ़्त certificate लगा सकता है। इसीलिए sbi-kyc-verify.xyz जैसी site पर भी ताला दिख सकता है। फ़ैसला domain नाम पढ़कर करें, ताले से नहीं।

एक और सीमा — HTTPS सिर्फ़ आपके और server के बीच है। Server के अंदर data कैसे सँभाला जाता है, किसे बेचा जाता है, या database कैसे सुरक्षित है — यह सब ताले से बाहर है। यानी HTTPS ज़रूरी है, पर काफ़ी नहीं।

Apni site par HTTPS lagane ke chaar kadam

1. Certificate लें। ज़्यादातर hosting में एक click में मुफ़्त Let's Encrypt certificate मिल जाता है। अगर server अपने हाथ में है, तो Certbot जैसा tool install करें जो certificate लेता है और auto-renew भी करता है।

2. Port 443 खोलें। Firewall या cloud security group में 443 allow होना चाहिए। Port 80 भी खुला रखें, क्योंकि Let's Encrypt उसी से domain verify करता है और redirect भी वहीं से होता है।

3. HTTP से HTTPS पर redirect करें। Server level पर 301 redirect सेट करें, ताकि पुराने links और typed URLs अपने आप secure version पर जाएँ। Apache में RewriteRule, Nginx में return 301 https://....

4. HSTS चालू करें। Strict-Transport-Security header browser को बताता है कि अगली बार सीधे HTTPS पर आना। इसे पहले छोटे max-age से test करें, क्योंकि गलत सेट होने पर browser काफ़ी देर तक site नहीं खोलेगा।

server {
  listen 80;
  server_name example.com;
  return 301 https://example.com$request_uri;
}

इसके बाद तीन चीज़ें जाँचें: सारे internal links https पर जा रहे हैं या नहीं, images और scripts भी https से आ रहे हैं या नहीं, और www वाला version भी सही certificate दिखा रहा है या नहीं। यही तीन जगहें सबसे ज़्यादा warning पैदा करती हैं।

Mixed content: taala aane ke baad bhi warning

Mixed content तब होता है जब page HTTPS से आता है पर उसके अंदर कोई image, script या stylesheet अभी भी http:// से लोड हो रही है। Browser इसे असुरक्षित मानता है, क्योंकि वह हिस्सा बीच में बदला जा सकता है।

आज के browsers active mixed content (scripts, iframes) को ब्लॉक कर देते हैं और passive content (images) पर warning देते हैं। इसे ठीक करने का तरीका सीधा है — code में हर जगह http:// को https:// करें, और जहाँ हो सके protocol-relative या relative URLs इस्तेमाल करें। फिर browser के Console में देखें; वह हर blocked request का पता देता है।

TLS 1.3 me kya naya hai

TLS 1.3 (2018) में पुराने और कमज़ोर algorithms हटा दिए गए — RC4, SHA-1 और static RSA key exchange जैसे। सिर्फ़ मज़बूत cipher suites बचे, इसलिए गलत configuration की गुंजाइश कम है। Handshake एक round trip में पूरा होता है, और 0-RTT से वापसी पर और भी तेज़।

एक नुकसान भी है: 0-RTT data replay हो सकता है, इसलिए इसे सिर्फ़ उन requests के लिए इस्तेमाल करें जिन्हें दोबारा चलाना सुरक्षित हो — जैसे page का GET. किसी payment या form submit के लिए नहीं।

Mera anubhav

एक बार मैंने नए server पर site शिफ़्ट की और ताला आ गया, पर mobile पर पुराना warning दिख रहा था। Desktop पर सब ठीक था। दो घंटे बाद पता चला कि certificate सिर्फ़ example.com के लिए था, www.example.com के लिए नहीं — और mobile browser मुझे www वाले version पर भेज रहा था। एक SAN entry जोड़ने से समस्या खत्म हो गई।

दूसरी बार एक client की site पर "Not secure" आ रहा था, जबकि certificate बिल्कुल नया था। कारण — एक पुराना analytics script http:// से लोड हो रहा था। Console में एक लाल line ने पूरी समस्या बता दी।

तीसरी बात जो मैंने सीखी: auto-renew को हर महीने जाँचना। Let's Encrypt के certificates 90 दिन के होते हैं और renewal अक्सर cron या systemd timer से होता है। एक बार वह timer चुपचाप fail हुआ और certificate expire हो गया — site पर कोई बदलाव नहीं हुआ था, फिर भी लोगों को warning दिखने लगा। अब मैंने एक reminder रखा है कि हर महीने एक बार expiry date देख लूँ।

नतीजा

HTTPS वही HTTP है, पर TLS के ऊपर — data encrypted, पहचान verified और रास्ते में बदलाव पकड़ा जाता है। Handshake में browser server का certificate जाँचता है और दोनों एक session key पर सहमत होते हैं; असली data उसी तेज़ symmetric key से जाता है। ताला भरोसे का संकेत है, ईमानदारी का सबूत नहीं। अपनी site पर मुफ़्त certificate लगाएँ, redirect और HSTS सेट करें, और mixed content साफ़ करें।

आगे पढ़ें: internet कैसे काम करता है — जहाँ DNS और HTTP का पूरा सफ़र है, और DNS records — जहाँ बताया है कि domain किस server पर जाएगा, यह कैसे तय होता है।

अक्सर पूछे जाने वाले सवाल

क्या HTTPS से site धीमी होती है?

पहले थोड़ा handshake जुड़ता है, पर HTTP/2 और HTTP/3 के लिए HTTPS ज़रूरी है, इसलिए कुल मिलाकर site तेज़ होती है।

SSL और TLS एक ही हैं?

SSL पुराना नाम है; आज जो चलता है वह TLS है। लोग बोलचाल में SSL कहते हैं।

मुफ़्त certificate कमज़ोर होता है क्या?

नहीं। Let's Encrypt वही encryption देता है जो paid certificate देता है; फर्क सिर्फ़ validation के level और support में है।

क्या ताला होने से site हैक नहीं हो सकती?

नहीं। HTTPS रास्ते को सुरक्षित करता है; server, code और database की सुरक्षा अलग विषय है।

Certificate expire हो जाए तो क्या होता है?

Browser पूरा warning page दिखाता है और ज़्यादातर लोग site छोड़ देते हैं। इसलिए auto-renew और reminder दोनों रखें।
