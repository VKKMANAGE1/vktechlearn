पिछले दो साल में AI चैटबॉट से आगे बढ़कर "agent" शब्द हर जगह आ गया है — लेकिन ज़्यादातर लोगों के लिए यह अब भी धुँधला है। क्या agent सिर्फ़ चैटबॉट का नया नाम है? नहीं। फर्क एक ही बात में है: चैटबॉट जवाब लिखता है, agent काम करता है। वह खुद तय करता है कि कौन सा tool चलाना है, नतीजा देखता है, और अगला कदम उसी हिसाब से बदलता है।

इस guide में मैं agent की पूरी बनावट खोलूँगा — चार हिस्से, एक असली काम का step-by-step उदाहरण, अकेला agent बनाम multi-agent, tools और MCP, पाँच use cases, और वे जोखिम जिनकी वजह से कई agent projects production तक नहीं पहुँचते। अगर आप अपने काम के लिए agent बनाने की सोच रहे हैं, तो यह पोस्ट आपको शुरुआत से पहले ही सही सवाल पूछना सिखा देगी।

छोटा जवाब: AI agent एक ऐसा system है जिसमें भाषा model के साथ tools, memory और एक loop होता है। Model सोचता है, tool चलाता है, नतीजा देखता है और जब तक काम पूरा न हो तब तक दोहराता है। यह तब फायदेमंद है जब काम कई कदमों का हो और हर कदम का नतीजा अगला कदम तय करे। जहाँ एक साफ़ prompt काफ़ी है, वहाँ agent बनाना सिर्फ़ खर्च और जोखिम बढ़ाना है।

AI agent क्या है: चैटबॉट से असली फर्क

चैटबॉट का काम एक turn में खत्म हो जाता है — आप पूछते हैं, वह जवाब देता है। Agent का काम कई turns में चलता है, और हर turn में वह अपने ही पिछले कदम का नतीजा पढ़ता है। इसे एक उदाहरण से समझें: "कल की बैठक का summary बनाकर टीम को भेज दो।"

चैटबॉट कहेगा — "मैं calendar और email access नहीं कर सकता, आप summary paste कर दें।" Agent calendar tool से बैठक ढूँढेगा, transcript tool से text निकालेगा, summary बनाएगा, email tool से भेजेगा, और वापस बताएगा कि किसे-किसे भेजा। बीच में अगर transcript न मिले तो वह खुद दूसरा रास्ता खोजेगा — रिकॉर्डिंग link, या आपसे एक सवाल।

यही "खुद रास्ता खोजना" agent की पहचान है। इसे autonomy कहते हैं। पर ध्यान दें — autonomy जितनी ज़्यादा, जोखिम भी उतना ज़्यादा। इसलिए अच्छे agents अंधेरे में नहीं दौड़ते; उनके हर कदम पर permission, limit और जाँच होती है।

Agent के चार हिस्से

हर agent, चाहे वह 50 lines का script हो या बड़ा enterprise system, इन्हीं चार चीज़ों से बनता है। इनमें से कोई एक कमज़ोर हुआ तो पूरा agent कमज़ोर हो जाता है।

1. Model (दिमाग़)

यह भाषा model है जो सोचता है — क्या करना है, कौन सा tool चलाना है, कब रुकना है। बड़ा model बेहतर planning करता है पर महंगा और धीमा होता है; छोटा model तेज़ होता है पर जटिल काम में भटक जाता है। ज़्यादातर teams एक बड़े model को planning के लिए और छोटे model को साधारण steps के लिए रखती हैं।

2. Tools (हाथ)

Tool एक function है जो model बुला सकता है — search, database query, file read, API call, calculator, code runner। Tool का description ही model के लिए "manual" है: अगर description अस्पष्ट है, model गलत tool चुनेगा। इसीलिए अच्छे agents में tools की संख्या कम और description बहुत साफ़ रखी जाती है।

3. Memory (याद)

दो तरह की memory होती है। Short-term — इस काम के दौरान का पूरा conversation और tool results, जो context window में रहते हैं। Long-term — पुरानी बातचीत, user की पसंद, पिछले फैसले, जो database या vector store में रखे जाते हैं और ज़रूरत पर वापस लाए जाते हैं। बिना long-term memory agent हर बार शून्य से शुरू करता है और वही गलती दोहराता है।

4. Loop (आदत)

यही agent का इंजन है: observe → plan → act → check → दोहराएँ। हर cycle में model को पता चलता है कि पिछले कदम का क्या नतीजा आया, और वह अगला कदम उसी हिसाब से लेता है। Loop के साथ एक stop condition ज़रूरी है — काम पूरा होना, step limit, या बजट खत्म होना। बिना stop condition agent घूमता रहता है और पैसा जलाता है।

एक असली काम: agent step-by-step कैसे चलता है

मान लेते हैं कि एक sales agent को कहा गया — "पिछले हफ़्ते के leads निकालो, जिन्होंने demo नहीं लिया, उन्हें personalized reminder भेजो।" अंदर क्या होता है:

  1. समझना: model काम को तीन हिस्सों में तोड़ता है — leads निकालना, filter करना, email भेजना। वह तय करता है कि पहले CRM tool चलेगा।
  2. Tool call: CRM से पिछले हफ़्ते के 84 leads आते हैं, साथ में हर lead का status।
  3. जाँच: model नतीजा पढ़ता है और देखता है कि status field कुछ जगह खाली है। वह अनुमान नहीं लगाता — वह दूसरा tool (activity log) चलाकर वह जानकारी भरता है।
  4. Filter: 31 leads बचते हैं जिन्होंने demo नहीं लिया। model खुद से कोई नाम नहीं जोड़ता; सूची tool के नतीजे से आती है।
  5. Draft: हर lead के लिए छोटा संदेश बनता है, company के नाम और पिछली बातचीत के हवाले से।
  6. Approval: भेजने से पहले सूची और drafts इंसान को दिखते हैं — यही सबसे ज़रूरी कदम है।
  7. Send और log: मंज़ूरी के बाद email tool चलता है और हर भेजे गए संदेश का record बनता है।

ध्यान दें कि हर कदम पर model को tool का नतीजा दिखता है। यही चीज़ agent को भरोसेमंद बनाती है — वह अंदाज़े से नहीं, आँकड़ों से चलता है। और जहाँ जानकारी नहीं मिली, वहाँ उसने दूसरा रास्ता लिया, न कि कहानी गढ़ी।

अकेला agent, workflow या multi-agent

हर जगह multi-agent की ज़रूरत नहीं होती। तीन स्तर हैं और ज़्यादातर काम पहले दो में ही हो जाते हैं।

तरीकाकब सहीनुकसान
Fixed workflowकाम के कदम पहले से तय हैंनए हालात में नहीं ढलता
Single agent + toolsकाम कई कदम का है पर एक ही domain काबहुत लंबे काम में भटक सकता है
Multi-agentअलग-अलग हुनर चाहिए (research + coding + review)महंगा, धीमा, coordination मुश्किल

अनुभव यही कहता है: पहले workflow बनाएँ, फिर उसमें जहाँ ज़रूरत हो वहाँ agent डालें। Multi-agent तभी जब हर sub-agent का काम साफ़ अलग हो और उनके बीच का contract तय हो। वरना आपको ऐसा system मिलेगा जिसमें चार agents एक-दूसरे को गलत जानकारी देकर आत्मविश्वास से गलत नतीजा दे रहे हैं — और debug करना लगभग असंभव हो जाता है।

Tools और MCP: agent को दुनिया से जोड़ना

Agent की ताकत उसके tools से आती है। Tools जोड़ने के तीन तरीके हैं। पहला — सीधे code में functions define करके model को schema देना। दूसरा — किसी framework (LangGraph, OpenAI Agents SDK, CrewAI) का tool interface इस्तेमाल करना। तीसरा — MCP (Model Context Protocol), जो tools को एक standard server के रूप में उपलब्ध कराता है, ताकि वही tool कई अलग clients में चले।

MCP का फायदा यह है कि आप एक बार database या file server का MCP server बनाते हैं और वह किसी भी compatible assistant में काम करता है। नुकसान यह है कि हर नई परत debugging मुश्किल करती है — जब जवाब गलत आए, तो पता लगाना पड़ता है कि गलती model में है, tool में, या उनके बीच के description में।

Tools देते समय तीन नियम याद रखें: हर tool का काम एक ही हो, description में बताएँ कि यह कब इस्तेमाल करना है और कब नहीं, और वही जानकारी लौटाएँ जो अगले कदम के लिए ज़रूरी है — पूरा database dump नहीं।

Agent कहाँ असल में काम आता है

1. Research और summarization

कई sources खोजना, पढ़ना, तुलना करना और एक report बनाना — यह agent का सबसे स्वाभाविक काम है, क्योंकि हर source का नतीजा अगले source की दिशा बदलता है।

2. Customer support के पीछे का काम

Ticket पढ़ना, order status निकालना, policy देखना, जवाब का draft बनाना और इंसान को approval के लिए देना। यहाँ agent की भूमिका "जवाब भेजने वाला" नहीं, "तैयारी करने वाला" रखें।

3. Data की सफ़ाई और reporting

हर हफ़्ते अलग sources से data खींचना, mismatch ढूँढना, और उन्हें ठीक करने का सुझाव देना। जहाँ काम repetitive है पर हर बार थोड़ा अलग है, agent अच्छा चलता है।

4. Code और operations

Test चलाना, error पढ़ना, fix का प्रस्ताव देना, deploy से पहले checklist जाँचना। यहाँ सबसे ज़रूरी है sandbox — agent को production पर सीधा हाथ न दें।

5. Content workflow

Topic से outline, outline से draft, draft से SEO जाँच, और अंत में इंसान की editing। Agent speed देता है; taste और final ज़िम्मेदारी इंसान की रहती है।

जोखिम जिन्हें नज़रअंदाज़ नहीं करना चाहिए

गलत tool, सही आत्मविश्वास। Model गलत tool चुनकर सही लगने वाला नतीजा दे सकता है। इसलिए हर tool call का log रखें और output को schema से validate करें।

Loop में फँसना। बिना step limit और बजट limit के agent वही काम बार-बार करता रह सकता है। मेरी सलाह: हर task पर अधिकतम 10–15 steps और एक साफ़ abort condition।

Permission का दायरा। Agent को जितनी ज़रूरत है उतनी ही access दें। पढ़ने वाले काम के लिए write access देना सबसे आम और सबसे महंगी गलती है।

Prompt injection. अगर agent बाहर की website या email पढ़ता है, तो उसमें छिपी instruction उसे भड़का सकती है। बाहर से आए text को कभी निर्देश की तरह न मानें — उसे data की तरह treat करें, और खतरनाक कामों के लिए इंसानी मंज़ूरी रखें।

खर्च का अनुमान न लगाना। एक agent task में 20 model calls हो सकते हैं। इसलिए हर task का cost पहले नापें, फिर scale करें।

Production में ले जाने के पाँच नियम

  1. छोटा शुरू करें: एक tool, एक साफ़ काम, एक हफ़्ते का prototype।
  2. हर कदम log करें: कौन सा tool, क्या input, क्या output, कितना समय, कितना खर्च।
  3. इंसानी approval रखें: पैसा, email, delete और deploy — इन चारों पर हमेशा।
  4. Evaluation set बनाएँ: 30–50 असली tasks जिन पर हर बदलाव नापा जाए।
  5. Fail होने पर रुकने की आदत डालें: agent को पता होना चाहिए कि कब "मुझसे नहीं होगा" कहना है।

मेरा अनुभव

मैंने जो सबसे उपयोगी बात सीखी, वह model की नहीं, tools की थी। जब मैंने tools की संख्या 12 से 4 कर दी और हर description दोबारा लिखी, तो agent की सफलता दर एक हफ़्ते में साफ़ बढ़ गई। दूसरी बात — जिन tasks में agent अच्छा चला, वे सब "पढ़ो, तुलना करो, draft दो" थे; जिनमें वह गलत हुआ, वे "आख़िरी फैसला लो" थे। इसलिए आज मैं agent को फैसला लेने वाला नहीं, तैयारी करने वाला रखता हूँ।

तीसरी बात, जो सबसे ज़्यादा मायने रखती है: agent को एक साफ़ लिखा हुआ SOP दें। जिस काम के कदम आप किसी इंसान को समझा सकते हैं, वही काम agent को भी समझाया जा सकता है। जो काम आप खुद नहीं समझा पाते, वहाँ agent भी नहीं चलेगा — वह सिर्फ़ आपकी उलझन को तेज़ी से दोहराएगा।

नतीजा

AI agent कोई जादू नहीं, एक साफ़ engineering pattern है: model + tools + memory + loop, और ऊपर से permission, limit और जाँच। यह वहाँ चमकता है जहाँ काम कई कदम का है और हर कदम का नतीजा अगला कदम तय करता है। और यह वहाँ नुकसान देता है जहाँ एक अच्छा prompt या एक साधारण workflow काफ़ी था। शुरुआत छोटी रखें, tools कम रखें, log पूरे रखें — बाकी सब iteration है।

अक्सर पूछे जाने वाले सवाल

Agent और chatbot में एक लाइन में फर्क?

Chatbot जवाब देता है, agent काम पूरा करने के लिए खुद tools चलाता है और अपने कदम बदलता है।

क्या agent बनाने के लिए coding ज़रूरी है?

No-code tools से शुरुआत हो सकती है, पर भरोसेमंद production agent के लिए tools, logs और permissions पर coding control चाहिए।

Agent कितने tools रखें?

जितने काम के लिए ज़रूरी हों — अक्सर 3 से 6. हर extra tool model के लिए उलझन और गलती की गुंजाइश बढ़ाता है।

क्या agent अपने आप पैसे खर्च कर सकता है?

तकनीकी रूप से हाँ, अगर आपने payment tool दिया है। इसलिए भुगतान वाले हर काम पर इंसानी approval और hard limit रखें।

MCP क्या है?

Model Context Protocol — tools और data sources को एक standard तरीके से जोड़ने का open protocol, ताकि वही server कई अलग AI clients में चले।
